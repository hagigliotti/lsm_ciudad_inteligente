Revisión: 3 de noviembre de 2026

Seguridad

El proyecto tiene dos partes. El sitio que estás leyendo es estático (GitHub Pages): no tiene servidor propio, ni usuarios, ni base de datos. La plataforma (carpeta plataforma/ del repositorio) es el servidor de referencia para la futura API vecinal. Abajo, cada punto revisado en las dos.

1. Validación de todo lo que escribe el usuario HECHO

  • Una sola función, validarIdea, valida en el navegador y en el servidor: tipo, largo mínimo y máximo, formato de email y nombre, tema dentro de una lista cerrada y como máximo 2 enlaces.
  • Se quitan caracteres de control y los que invierten la dirección del texto; se normaliza Unicode.
  • Nada de lo que escribe el usuario se inserta como HTML. El servidor rechaza JSON mal formado (400), tipos de contenido inesperados (415) y cuerpos de más de 16 KB (413).
  • Campo trampa invisible para frenar bots.

2. Rate limiting por usuario y por IP HECHO

  • Sitio: el navegador espera 45 s entre envíos y permite 3 por hora. Es solo una cortesía: el límite real lo pone el servidor de Web3Forms.
  • Plataforma: 60 pedidos por minuto por IP; 120 por minuto por usuario con sesión; el formulario, unos 3 por hora por IP; el inicio de sesión, 5 intentos y luego 1 por minuto. Al pasarse responde 429 con Retry-After.
  • Para varias instancias del servidor, los contadores pasan a Redis (está marcado en el código).

3. Tokens y sesiones: ¿alguien puede quedar conectado sin querer o ser suplantado? REVISADO

Sitio: no. No hay inicio de sesión, ni tokens, ni cookies propias. En el navegador solo se guarda la respuesta al aviso de cookies y la hora de los últimos envíos.

Plataforma: así se evita cada riesgo:

RiesgoCómo se evita
Quedar conectado sin quererLa sesión vence a los 30 minutos sin uso y a las 8 horas sí o sí. Cerrar sesión la borra del servidor, no solo del navegador.
Sesiones viejas olvidadasAl iniciar sesión se cierran las anteriores del mismo usuario.
Robo del token por JavaScript (XSS)Cookie HttpOnly: el JavaScript de la página no la puede leer.
Envío del token sin cifrarCookie Secure con prefijo __Host- y HSTS: solo viaja por HTTPS.
Suplantación desde otro sitio (CSRF)SameSite=Strict y CORS cerrado a la lista de orígenes.
Adivinar o falsificar un tokenToken aleatorio de 256 bits que no contiene datos. Un token inventado da 401 (hay una prueba para eso).
Robo de contraseñasGuardadas con scrypt y sal; comparación en tiempo constante; el mismo mensaje exista o no el usuario.

4. Rutas de la API: cuáles no tienen autenticación o validación REVISADO

Sitio: no tiene rutas de API propias. Su única salida de datos es el envío del formulario a Web3Forms, que se identifica con una clave pública (es así por diseño) y está protegido por validación, campo trampa y el límite del proveedor.

Plataforma: resultado de npm run auditar. Una prueba automática falla si aparece una ruta pública sin justificación o una ruta que recibe datos sin validarlos.

5. CORS HECHO

  • Sitio: al no tener API, no hay CORS que configurar. GitHub Pages sirve los archivos públicos a cualquier origen, lo cual es correcto para contenido público.
  • Plataforma: solo responde a los orígenes de la variable ORIGENES (por defecto, https://hagigliotti.github.io). Nunca usa * con credenciales. Un origen desconocido recibe 403 y ninguna cabecera CORS.

6. Otras protecciones

  • Política de seguridad de contenido (CSP) en cada página: solo se ejecuta código del propio sitio, y de Google únicamente si aceptaste estadísticas. Sin scripts ni estilos en línea.
  • Sin fuentes ni librerías de CDN externos: menos terceros que puedan ver tu visita o inyectar código.
  • La plataforma agrega nosniff, X-Frame-Options: DENY, no-store y HSTS.

7. Cómo se manejan los errores HECHO

  • El usuario ve un mensaje claro y un código de seguimiento, nunca un error técnico, ni rutas de archivos, ni versiones.
  • Los errores inesperados devuelven 500 con un mensaje genérico; el detalle va al registro interno con el mismo código.
  • Los registros nunca guardan contraseñas, cookies ni el texto de los formularios (hay una prueba que lo verifica).
  • En el sitio, si falla el envío, se explica qué hacer (revisar la conexión, esperar unos minutos) y el botón se reactiva.

8. Escalabilidad y pruebas siempre HECHO

  • npm test corre las pruebas de validación, de la plataforma (validación, límites, sesiones, CORS, errores, auditoría de rutas) y de cada página (CSP, enlaces rotos, textos alternativos, aviso de IA, Google Analytics solo con permiso).
  • GitHub Actions corre las pruebas en cada cambio. Si una falla, el sitio no se publica.
  • La plataforma no guarda estado en memoria para producción: sesiones y límites van a Redis, así se pueden sumar servidores detrás de un balanceador. La carga se planifica para 15.000 habitantes más la población flotante.

Pendientes antes de abrir la plataforma al público A HACER

  • Base de datos real y Redis para sesiones y límites.
  • Doble factor para cuentas de administración.
  • Prueba de intrusión externa y revisión de dependencias en cada versión.
  • Copias de seguridad cifradas fuera del servidor y un ensayo de recuperación.
